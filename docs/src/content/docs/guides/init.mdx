This chapter, we will be going through on how you can use Tungsten to help you initialize your project, along with some tips for folder structure!

## Adding your assets

Before you initialize your project, you need to add your assets into a folder that Tungsten can read from, duh!

Simply create some folders for your inputs, and drop your assets in!

And also create an `src` folder for storing the generated code!

### Best Structure Practices

Now sometimes Tungsten doesn't work nicely because of how you structured your folders, maybe you put a bunch of assets that are supposed to be separated together, multiple file formats in the same folder etc. So this section will tell you about good practices on structuring your project!

Some good practices are:

- **Don't dump every asset type in one flat folder.** Tungsten guesses type from folder context, so a flat folder gives it nothing to go on and everything falls back to the same default. That's the images converted to images, not decals bug.
- **Keep decals and generic images in separate folders.** File extension alone doesn't tell Tungsten what an image is for.
- If a folder genuinely needs a type that differs from its siblings, **use a .tmeta file to assign the type locally** instead of overriding it at the project level. That keeps the fix scoped to the folder that actually needs it.
- **One asset type per directory where possible.** Reach for .tmeta when a folder has to break that rule, not a global override.
- **Watch for folder or key names that collide with config namespacing.**

## Finally Initializing

Okay, you may think that you have to write your configuration file all by yourself, like Asphalt or Tarmac. Luckily for you, Tungsten has a built-in command for generating your configuration file!

All you have to do is run this command and it will prompt you with a few options:

```bash
tungsten init
```

The setup is extremely simple, the flow works like this:

<Steps>

1. **Set your creator types**
   1. Choose your creator type (`user` or `group`)
   2. Type in your creator ID
2. **Select the assets you want to be included in your inputs**
3. **Choose your codegen options**
   1. Select your style (`flat` or `nested`)
   2. Choose if you want to strip file extensions from names
   3. Choose if you want TypeScript declaration files (`.d.ts`) to be generated
4. **Ta-da!**

</Steps>

## Learning about your Configuration

After running `tungsten init`, you should have a `tungsten.toml` file in your project root. This file contains your configuration.

Now, what does your configuration actually contain? Let's do a quick rundown.

### Creator

The `creator` section contains information about your creator, including your creator type and ID.

```toml
[creator]
type = "user"
id = "123456"
```

### Codegen

The `codegen` section contains options for generating code.

```toml
[codegen]
style = "flat"
strip_extensions = false
ts_declaration = false
```

If you use the **Nested** style, you can access images like `images.searchbar.search(dpiScale)`. If you use the **Flat** style, you can access images like `images["searchbar/search"](dpiScale)`.

### Inputs

This is the most important part of the configuration. It defines what Tungsten knows about your assets and how it should handle them when syncing.

#### List of fields

Fields with the symbol * are required.

- `path`*: The path to where your inputs live.
- `output_path`*: The path to where the generated code should be saved.
- `type`: The asset type that Tungsten should sync as.
- `packable`: Whether or not Tungsten should pack your image assets into a spritesheet.
- `uniform_cells`: Whether Tungsten should use a uniform cell size for packing images rather than bin-packing, only applicable when `packable` is `true`.
- `cell_size`: The size of each cell in the spritesheet, only applicable when `uniform_cells` is `true`.
- `cell_fit`: The fit mode for the cell contents, only applicable when `uniform_cells` is `true`.
- `svg_scale`: The scale factor for SVG assets, only applicable when an asset is an SVG file.
- `bleed`: Whether Tungsten should apply alpha bleeding to your assets.

#### Web assets

Similarly to Asphalt, you can also define web assets in your configuration.

```toml
[inputs.icons.web]
"assets/icons/legacy_badge.png" = { id = 1234567890 }
```

This lets Tungsten know that the asset already exists on the Roblox marketplace, and that it should just skip uploading it and just generate the code with the specified asset ID.
